## Must fix

1. **Step 5 names routines the program never calls.** "fload/scrload"
   and "mvscr/mv2vram": scrload and mv2vram are on your own list of
   routines nothing calls (point 7 of round 1). load_pics calls fload
   (the file into the picmem buffer) and then mvscr (the buffer into
   VRAM at CS:[scr], 3E80h further for each picture). [scrst] belongs
   to the display side (setst, in disply_pics), not to loading. Write
   step 5 from load_pics alone.

2. **The picmem gap has the same mistake.** "load segment for
   fload/scrload, presumably": it is the segment of the picture buffer
   that intro gets from malloc, which load_pics passes to fload and to
   mvscr and which intro gives back with mfree. It is read at CODE:0030,
   CODE:0129 and CODE:013A (the last one is missing from the notes). The
   code shows all of this, so drop the "presumably".

3. **ldfail on the early failure paths.** The notes call ldfail
   "cleanup+exit". Trace what it does on each path that jumps there and
   write down what the code shows:
   - getcmdline fails or malloc fails (CODE:0013, CODE:0021) before
     setkbdint has run: rstkbdint then sets INT 9 from [oldint] and the
     word after it, which nothing has written (they start as zeros in
     DATA). The keyboard vector would then point to 0000:0000.
   - Every path before disply_pics (the three above plus fload failing
     in load_pics): GetCDDrive has not run yet (only GetDiskInfo calls
     it, from GetSNL in disply_pics), so DoStopTrack sends its request
     with [drivenumber] still 0.
   - On the normal path DoStopTrack runs twice (at the end of
     disply_pics and again in ldfail).
   - The exit code is always 0 (`MOV AX,4C00H`). The program never sets
     a text mode again: it ends in Mode X with the palette black (dispoff
     at the end of disply_pics).
   Put this in the notes (a short "ldfail" paragraph, and replace the
   "cleanup+exit" line under "Uncertain"). Nothing here was run, so say
   it comes from reading the code. It matters for the port, which must
   not copy the INT 9 problem.

4. **Comments that hedge on what the code shows, or get it wrong.**
   - CODE:01F0 getcmdline: BX is the PSP segment (from INT 21h AH=62h in
     intro), and the routine reads ES:0080h with ES=BX, not "ES:BX+80h".
     BL = the first non-blank character minus 30h is in the code (drop
     "presumably"). Only characters below '0' are rejected (`JNS`), and
     an empty command tail (length byte 0) sets CF.
   - CODE:010A load_pics: it also copies each picture into VRAM with
     mvscr (see 1). Say so and drop "presumably".
   - CODE:06A3 fld2vram: it does call mv2vram (visible, not "presumably
     copy to VRAM next"), and the 2 and 3 it puts into AX before
     `JMP ldfail` are lost, because ldfail loads AX=4C00h.
   - CODE:08EC GetQInfo: it returns AL = bit 1 of the byte at DATA:0370,
     the high byte of [Status] (bit 9 of the request header's status
     word). In the DOS device driver request header, bit 9 is "busy".
     Say that the code tests that bit, and that it means busy according
     to the device driver specification (not checked by running). Then
     step 9 can say what it tests: disply_pics shows the fourth picture
     while the drive reports busy, presumably while the track is still
     playing.
