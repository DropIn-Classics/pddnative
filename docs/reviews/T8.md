# Review of T8, round 1 (branch `sol/T8-gfx` at 640053b)

Checked from the main checkout: only `tools/gfxfiles.py`,
`src/DDPCINTR.hints`, `src/DDPCMAIN.hints` and `docs/tasks/T8.md`
changed. Both hints files build IDENTICAL. The branch's `gfxfiles.py`
parses and re-encodes all seven DELUXE `.VGA`, the three `.SPR` and the
eight `TABLE2M` files with exit code 0. The readers in the notes are
right. The swap of `background_path`/`icon_path` is right: OPTIONS:0191
holds `ddpcbkgd.vga`, 019E holds `ddpcicon.spr`, and `options_init`
reads them into 0632h and 0625h. The table palette offsets and lamp
counts are the ones the eight `setup_*` routines store. The intro and
menu pictures look right with their palettes.

The table palettes are wrong, though, on both programs. This went
unnoticed because `TABLE2M.IGN`, the one picture that was looked at,
uses no colour above BFh. The finding comes from screenshots of the
original (`tools/run.py ... -shot`). The table picture is found in each
screenshot by trying every scroll position until each colour index maps
to one screen colour. Then each index's colour on screen is compared
with the tool's palette.

## Must fix

1. **PD2's `set_palette` (CODE:49FE) is not PD's.** It sends 300h bytes,
   all 256 colours, straight from `ES:[table_palette]` (`REP OUTSB`),
   with no black fill and no repeated ranges. Colours 40h..7Fh of that
   block are `lights_off_pal` (`table_palette` + 0C0h). Each PD2 table's
   set-up writes them first through `make_off_colours` (CODE:4B54):
   0C0h bytes, each half the byte at `lights_on_pal`. The bytes in
   PD2.EXE at that place are not those values (129 to 177 of the 0C0h
   bytes differ, per table). `gfxfiles.py` builds PD2's palette the way
   PD does and reads the static bytes.
   - Evidence: Neptune (PD2.EXE table 0), screenshot at t = 4 s, scroll
     215. 93 colour indices are visible, and the tool's palette gets 60
     of them wrong (more than 2 off in a component). A palette of the
     300h bytes, with 0C0h..17Fh replaced by `make_off_colours`' result,
     gets 88 right. The other 5 are lamps lit at that moment (twice the
     off colour).
   - What to do: for PD2, use the 300h bytes at `table_palette` with
     `make_off_colours` applied. That also fixes the PD2 `FLIPPERS.SPR`
     previews. Correct the notes' table row, which says the palette is
     assembled "as `set_palette` at `CODE:49FE` does".

2. **PD's `set_palette` (CODE:4B39) repeats the first 40h colours
   twice.** After the black fill it does `POP SI / PUSH SI` before the
   second pass and `POP SI` before the third. Both passes therefore send
   source colours 0..3Fh: to 80h..BFh and again to C0h..FFh. The tool
   sends 40h..7Fh to C0h..FFh.
   - Then it sets colours FEh and FFh by `opt_palette`: 1 gives 10,10,10
     and 3F,3F,3F; otherwise 14,0A,05 and 3C,1E,0F.
   - Evidence: Beat Box (PD.EXE table 2), screenshots at t = 15 s and
     25 s (scroll 30 and 40). 10 indices at C0h or above are visible, all
     10 differ from the tool's palette, and all 10 match the repeated
     first 40h.
   - What to do: fix the C0h..FFh range and set FEh/FFh as the code does.

3. **Say which options the previews show.** With `opt_palette` 1,
   `grey_palettes` (PD CODE:4DEF, PD2 CODE:4CD5) makes the table and
   lamp palettes grey before `set_palette`. The default (DDPCOPTN.BIN
   missing) is 2, the colour set. Say in the tool's docstring and in the
   notes that the previews are the default colour setting. An option for
   the grey one is welcome but not required.

4. **Check the palettes against the original.** Take one screenshot of a
   PD2 table and one of a PD table where colours at C0h or above are on
   screen (Beat Box at t = 15 s with `-shot`, for example). Compare them
   with the preview, and write in the notes what was compared and the
   result. `tools/run` is there for this. "Looks right" was not enough
   here.

5. **`options_init` and its callees run with DS = OPTIONS**
   (`options_screen` sets it at CODE:142D), but no `ds` hint covers
   them. So the listing writes the names this task added as DATA labels:
   `[D019E]`, `[D0191]`, `[D0625]`, `[D0632]` in `options_init`, and
   `[D0301]` where `options_palette` is loaded (in `options_init` and at
   L2F04). What to do: add `ds ... OPTIONS` hints for the
   routines that run with DS = OPTIONS, as in T7. The build must stay
   IDENTICAL. Afterwards those five `D` labels must be gone from
   `build/DDPCMAIN.ASM` where DS is OPTIONS.
