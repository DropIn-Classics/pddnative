# T5: table-program data files

Branch `sol/T5-pdfiles`. Files: `tools/pdfiles.py`, this notes file.

Work started from master. The tool will parse and re-encode every
TBLDETLO/TBLDETHI collision map, render false-colour PNG previews, and
decode the PD/PD2 high-score files and DDPCOPTN.BIN according to the
formats documented in `src/PD.hints`.

## Tool

`tools/pdfiles.py` has three subcommands:

- `map FILE [--png OUT]` decodes all 512 rows and their two x halves,
  prints counts by surface and the event/code counts for surface 1Fh,
  re-encodes the records and requires byte-for-byte identity. The PNG
  is a 320x512 standard-library RGB image with one colour per surface.
- `hiscores FILE` prints the four ranked entries for each of the four
  tables. Each entry is three initials and six big-endian packed-BCD
  bytes (twelve decimal digits).
- `options FILE` prints the four choices, four key-map words and screen
  byte. A key word stores the byte index first and the one-bit mask
  second; the tool also prints the resulting scan code.

Read from PD.EXE, not checked by running: `collision_response` and
`surface_params` use the low nibble for the response and five-word
parameter-table entry. In `surface_params`, only high nibbles exactly
10h and 20h select the two kicker score records; 30h and 40h match
neither and add no other effect. Thus 33h/36h/37h use the same collision
parameters as 03h/06h/07h. Surface 42h uses the low-nibble-2 entry but,
because the whole byte is not 02h, does not take the special moving
right-flipper path.

The DREAMS2 maps therefore also contain low nibble 0: TBLDETLO.SFR has
10h (216 pixels), 20h (141) and 30h (122), while TBLDETLO.UND has 10h
(184) and 20h (114). Low nibble 2 occurs as surface 42h in
TBLDETLO.STT (49 pixels). This fits the `surface` comment at DATA:9776:
`surface_params` maps both low nibble 0 and 1 to the first parameter
entry; low nibble 2 selects the second entry.

DREAMS1/TBLDETHI.BBX also has one 1Fh pixel whose angle byte is 80h, at
(82,33), rather than one of the documented 00h..0Fh event numbers.
Read from PD.EXE, not checked by running: `map_code` does not bound an
unrecognised value and returns 80h unchanged; `map_special` stores it in
`map_event`. `map_event_run` later doubles that byte to form a word-table
offset. 80h therefore wraps to offset 00h and selects the same first
`map_events` pointer as event 0. There is no bounds check before the
table lookup.

The uncommitted previews `build/TBLDETLO.IGN.png` and
`build/TBLDETHI.STW.png` were inspected. The first clearly outlines the
whole table, bumpers, lanes, slings and flipper area; the second shows
the upper ramp/loop. They look like collision geometry for the tables.

## High scores and options

Both 144-byte HISCORES files print four plausible ranked scores for all
eight tables. PD1 contains shipped entries with blank initials and
scores 18634310 (Steel Wheel) and 5700000 (Beat Box); the remaining
initials identify their tables. All score bytes are valid packed BCD.

The CD has no DDPCOPTN.BIN because the menu creates it. The options
decoder was checked with the menu's defaults from CODE:2BEB: it reports
three balls, game-controlled music, colour, gravity 9, Left Shift,
Right Shift, Space, E0 Down and 320x200.

## Differences from `PD.hints`

At the initial T5 verification, the hints called DDPCOPTN.BIN 14 bytes
and described `opt_screen` as a word. DDPCMAIN's `load_options` at
CODE:2BEB requires a 13-byte file and `save_options` at CODE:2CFE writes
0Dh bytes: four choice bytes, four key words and one resolution byte.
`pdfiles.py` follows that writer. PD.EXE loads the byte at DATA:9AA2;
the following byte is merely the zeroed storage beside it. The lead
corrected that comment on master during review.

The collision-map disagreements found during review are all listed
above: high nibbles 30h/40h, low nibbles 0/2, and the 1Fh angle/event
byte 80h. No high-score file disagreed with its comments.
