## What the program does (checked against the code)

1. Shrink memory (mstart2 via msize: ES=CS-10h to DX paragraphs).
2. Read the CD track number from the command line (getcmdline parses
   the PSP digit).
3. Allocate the picture buffer (malloc).
4. Set Mode X 320x200 (init320200) and install the keyboard handler
   (setkbdint sets INT 9 to kbdint).
5. Load the four pictures: load_pics calls fload for the file into the
   picmem buffer, then mvscr for the buffer into VRAM at CS:[scr],
   3E80h further for each picture. [scrst] belongs to the display side
   (setst, in disply_pics), not to loading.
6. Free the buffer (mfree).
7. Start the track (DoPlayTrack via GetStartLen and MSCDEX INT 2Fh).
8. Show three pictures, each faded up (fadeup), held for its delaytable
   time (disply_pics_bb loop with waitframe 1), then faded down
   (fadedn); a key jumps to disply_pics_dp020 and ends the whole show.
9. Show the fourth while the drive reports busy: disply_pics calls
   GetQInfo and shows it again while AL returns 2, presumably while the
   track is still playing.
10. Fade down (fadedn), stop the track (DoStopTrack), dispoff (palette
    to black) in disply_pics before it returns; then ldfail runs
    DoStopTrack a second time, then rstkbdint and exit (INT 21h AH=4Ch).

Nothing was checked by running; jobs marked presumably in the `comment`
hints are inferred from INTs/ports/names.

## ldfail on the early failure paths (from reading the code, nothing run)

`ldfail` (CODE:003E, also named `exit`) does DoStopTrack, rstkbdint,
then `MOV AX,4C00H` and `INT 21h`. Traced on each path that jumps there:

- getcmdline fails (CODE:0013) or malloc fails (CODE:0021) before
  setkbdint has run: rstkbdint then sets INT 9 from `[oldint]` and the
  word after it, which nothing has written (they start as zeros in
  DATA; only setkbdint writes them). The keyboard vector would then
  point to 0000:0000. The port must not copy this INT 9 problem.
- Every path before disply_pics (the two above plus fload failing in
  load_pics at CODE:0137): GetCDDrive has not run yet (only GetDiskInfo
  calls it, via GetSNL in disply_pics, verified sole caller at
  CODE:0745), so DoStopTrack sends its request with `[drivenumber]`
  still 0 (DATA starts zeros; only GetCDDrive writes it).
- On the normal path DoStopTrack runs twice (at the end of disply_pics
  at CODE:00FD and again in ldfail at CODE:003E).
- The exit code is always 0 (`MOV AX,4C00H`); the program never sets a
  text mode again: it ends in Mode X with the palette black (dispoff at
  the end of disply_pics at CODE:0103).

## Corrections after the merge (Claude, from reading the code)

Three points in the notes above were wrong or incomplete. The first two
came from Claude's round-2 review, not from Muse:

- DoStopTrack runs three times on the normal path, not twice: in
  disply_pics right after GetSNL (before DoPlayTrack; GetCDDrive has run
  by then, so `[drivenumber]` is set), at the end of disply_pics
  (CODE:00FD), and in ldfail. Step 7 is really: GetSNL, DoStopTrack,
  DoPlayTrack with `[track]`, all in disply_pics.
- getcmdline has a third outcome: a command tail of blanks only (length
  byte not 0, then spaces up to the CR) takes the `0Dh` branch to
  getcmdline_gcl100 with CF clear, and BL gets whatever AL holds. AL is
  the low byte of DATA's segment value (intro's `MOV AX,DATA`; mstart2
  keeps AX with PUSHA/POPA; INT 21h AH=62h presumably leaves AL alone,
  not checked). So `[track]` is then a meaningless number. `JNS` also
  rejects characters from B0h up (the difference is negative as a signed
  byte), and any character from '0' to AFh passes, letters included.
  The `comment` on CODE:01F0 in the hints is corrected accordingly.
- One more early path to ldfail: mfree failing in intro (after
  load_pics). setkbdint has run there, so INT 9 is restored properly;
  `[drivenumber]` is still 0.
